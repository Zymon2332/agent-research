# 能力、痛点与未来：一张可核对的总表

## 一句话结论

单步能力已经越过"能用"线，真正的瓶颈移到三处：**组合可靠性、单位成本、组织治理**。未来 1–3 年的增量主要来自 harness 与评测基础设施，而不是再来一次模型换代——因为模型变强不会自动修复边界上的信息损失，也不会自动产生审计与计费。

## 问题与边界

- **解决什么**：把散在各篇的"过去能做什么、现在卡在哪、未来会怎样"收成三张表：能力刻度、痛点矩阵、未来情景。
- **不解决什么**：不重复技术代际的叙事（见[四代演进](02-evolution.md)），不展开单个缺口的证据链（见[开放问题](../06-outlook/01-open-problems.md)），不做产品预测。
- **为什么单独成篇**：演进篇按"技术"分段，本篇按"能力"分段；前者解释为什么长成这样，后者回答"现在到底能干什么、还差什么"。

## 能力刻度

| 维度 | 2023 | 2024 | 2025 | 2026（可核证据） |
|---|---|---|---|---|
| 典型任务长度 | 单步问答 + 1–2 次工具 | 10 步内的检索与写作 | 小时级编码、研究任务 | 12 小时 @50%，1 小时 @80%（METR） |
| 工具面 | 少量函数 | 10–20 个 API | MCP 接入 + computer use | 50+ 工具 + 检索/网关治理 |
| 交互形态 | 聊天 | 聊天 + 插件 | 编码 CLI、浏览器 | 常驻调度 + 事件驱动（探索中） |
| 自主度 | 每步确认 | 关键点确认 | 长任务少干预 | 无人 @ 也可能主动行动 |
| 成本口径 | 按 token 计价 | 按任务估算 | 按任务 + 缓存 | 开始要求 cost per success |
| 可审计性 | 应用日志 | trace | OTel 语义约定 | 审计事件草案（GAR 等） |

说明：2023–2025 三列是定性概括，用于建立趋势；2026 列尽量给可核数字。任务长度的两个口径不能混用——对外演示常用 50%，生产容量要按 80% 算（[METR Time Horizon 1.1](https://opendatascience.com/ai-agent-task-horizon-workforce-planning/)）。

## 当前能力：三层漏斗

| 层 | 2026 年的状态 | 证据 | 缺口 |
|---|---|---|---|
| 单步能力 | 接近饱和，benchmark 开始"修尺子" | SWE-bench Verified 因污染与测试缺陷被弃用；OSWorld 头部 79.6%、中位 53.4% | 分数与真实体验脱节 |
| 组合可靠性 | 长任务成功率随步数乘性衰减 | 30 步 × 95% ≈ 21%；多 agent 的 15 倍 token 只换来有限提升 | 缺小时级、可中断、带成本的公开基准 |
| 组织治理 | 身份与审计仍在草案阶段 | 厂商有 Entra Agent Identity 等方案，IETF 有 Trust Profile / GAR 草案 | 跨平台格式与责任边界未定 |

三层的关系不是流水线，而是**下一层会否定上一层**：benchmark 再高，过不了治理就上不了线；治理再全，组合可靠性不够就会持续产生人工接管成本。

## 痛点矩阵

| 痛点 | 根因 | 现有缓解 | 仍缺什么 | 谁最痛 |
|---|---|---|---|---|
| 长任务评测 | 判定成本随长度上升，环境不可重置 | 分段评测、回放、影子流量 | 公开的小时级基准 | 平台与采购 |
| 成本归一 | 多 rollout、长思考让同分不同价 | 榜单开始列 cost 列 | cost-per-success 统一口径 | 采购与财务 |
| 上下文膨胀 | 长上下文边际收益递减，工具定义占预算 | compaction、检索式工具、子 agent 隔离 | 压缩质量的自动度量 | 所有长任务团队 |
| 记忆不可控 | 写入容易、遗忘与冲突难 | 文件式记忆、向量检索、后台整理 | 写入质量基准与删除证明 | 产品与合规 |
| 间接注入 | 工具结果与网页都是不可信输入 | 权限收窄、沙箱、审批门 | 内容来源的强制标记 | 安全与平台 |
| 身份不清 | agent 代表谁行动没有通用答案 | OAuth 交换、厂商身份服务 | 跨协议标准 | 企业与治理 |
| 审计缺失 | 没有统一的事件 schema | 自建 trace + 映射 | 行业级审计格式 | 金融、医疗 |
| 协议经济层空白 | 计费、发现、信任未定稿 | x402、IETF 发现草案、Trust Profile | 定稿与互认 | 跨组织协作 |
| harness 锁定 | 无标准接口，迁移等于重写 | 自建抽象层、插件化 | 可移植的 harness 接口 | 平台团队 |
| 审批疲劳 | 全量审批导致"无脑通过" | 动作分级、高风险才拦 | 风险自适应的阈值 | 运维与合规 |

矩阵读法：**根因一列如果写着"没有标准"，说明短期只能靠工程手段，不要等生态**；如果写着"成本/注意力"，说明要靠产品设计而不是技术选型。

### 读数字的三种证据

| 证据类型 | 例子 | 可信度 | 常见偏差 |
|---|---|---|---|
| 论文 / 受控实验 | METR、MAST、τ-bench | 高（方法可查） | 任务分布窄、成本未计 |
| 公开榜单 | OSWorld、SWE-bench、Terminal-Bench | 中（复现性参差） | 脚手架差异、污染、选择性提交 |
| 厂商 / 产品自述 | 90.2%、15 倍 token、79.6% | 低到中（口径不透明） | 内部评测、取最优一次、成本不披露 |

用法：**用论文判断方向，用榜单做横向，用自述了解产品边界**；任何单一来源都不足以支撑选型。

### 按角色看痛点

| 角色 | 最痛的三条 | 现在能做什么 |
|---|---|---|
| 产品 | 长任务成功率、接管体验、成本 | 先定业务口径，再选 benchmark |
| 平台 | 身份、审计、沙箱、harness 锁定 | 把治理做成可替换适配层 |
| 采购 | 分数不可比、成本不透明 | 要求 cost per success 与失败分类 |
| 治理 / 合规 | 责任、删除权、留痕 | 动作分级 + 全量 trace |

## 未来：三档情景

### 大概率（12–18 个月）

- **harness 商品化**：协议已把连接标准化，托管 runtime 的计费细到 vCPU·hr 与 GiB·hr，资源型能力难有长期溢价。
- **评测 CI 化**：SWE-bench 被弃用、Terminal-Bench 加固 verifier、WebArena 重做判分，说明评测需要像测试一样持续维护。
- **子 agent 成为标准件**：隔离上下文 + 只回摘要的模式已在各家产品中出现，不再是"高级玩法"。
- **MCP 扩展化**：Tasks、Apps、企业授权以扩展形式演进，核心协议进入慢节奏。

反证条件：某个 runtime 通过独占工具生态形成网络效应；或模型出现跨代跃迁，把 harness 的一部分能力吸收掉。

### 有可能（18–36 个月）

- **跨组织 agent 身份出现事实标准**：OAuth 令牌交换、SPIFFE/WIMSE、Trust Profile 几股力量收敛。
- **记忆写入有规范**：至少出现"可审计写入 + 可验证删除"的行业约定。
- **审计事件 schema 落地**：从各家自建走向可归集的格式。
- **计费与发现**：x402 类方案与 IETF 发现草案跑出可用实现。

反证条件：治理节奏继续落后于能力节奏；或大厂各自封闭生态，标准被边缘化。

### 不太可能（3 年以上）

- **通用全自动 agent**：长任务成功率仍随步数衰减，且验证成本高于生成成本。
- **跨组织责任制度**：法律主体、保险、追责链条都没有对应物。
- **agent 法律人格**：目前只有讨论，没有可执行框架。

> 判断：把"不太可能"一列写出来，是为了防止两种错误——用长期问题否定当下投入，或用短期 demo 承诺长期能力。

### 三个可观测信号

如果未来 12 个月出现这三个信号，说明"工程化"这条线真的成立：

1. 主流榜单默认带 cost 列，且能按成功任务归一。
2. 至少两家云厂商采用同一份 agent 审计事件 schema。
3. 出现可移植的 harness 适配层（同一套技能与工具定义能跨 harness 复用）。

反过来，如果只有模型分数在涨、这三样没动，说明瓶颈仍在原处。判断趋势时，**看基础设施的采用率，不要看发布会的口号**。

## 三个约束：为什么能力不会线性外推

1. **人的注意力**。一个人通常只能同时跟进 3–5 个活跃会话，多任务上限已经从模型转移到人（[Super-agent 设计探索](https://finance.sina.com.cn/roll/2026-11-01/doc-inixeyiz3146996.shtml)）。
2. **验证成本**。生成一个方案很便宜，判断它对不对很贵；任务越长，验证占的比例越高。
3. **治理节奏**。能力按月迭代，治理按年协商；"能连"总会跑在"能管"前面。

这三条决定了：**能力曲线的斜率会放缓，但可用性的提升空间仍然很大**——后者靠工程，不靠模型。

## 对团队的启示

- **容量规划按 80% 口径**，不要把"能连续工作 12 小时"当成生产能力。
- **投资顺序**：评测数据 > 上下文工程 > 权限与沙箱 > 框架选型。前三条是复利，最后一条可替换。
- **成本看 cost per success**，不看 token 单价；后者会把"便宜但老失败"的方案算成最优。
- **每季度复核一次基线**：本篇与各篇的数字都带 2026-11 的时间戳，半年后必须重核。

## 开放问题

- **能力刻度能否量化**：除了任务时长，是否还有"工具数 × 自主度 × 可审计性"的复合指标？
- **评测的公共品属性**：独立评测由谁付费？厂商、买家、监管的激励都不足。
- **治理的先行者收益**：早做审计与身份的企业，能否在采购与合规上获得溢价？
- **人机协作的度量**：接管率、接管时长、信任恢复时间，目前没有统一口径。
- **能力与成本的剪刀差**：能力提升往往伴随成本上升，"每美元能力"该怎么算？
- **评测的时效性**：基准的半衰期有多长？是否需要像依赖一样做版本钉住？
