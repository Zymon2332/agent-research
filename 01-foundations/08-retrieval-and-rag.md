# 检索与 RAG：把"找证据"做成可迭代的工具

## 一句话结论

RAG 的瓶颈不在向量库，而在**查询构造、召回质量、证据使用**这三段；在 agent 里，检索应该被当成一个可多次调用的工具，而不是一次性的前置步骤——因为模型往往在读到第一批证据之后，才知道该问什么。

## 先看一次"三年前的公告"

用户问："退款多久到账？" 检索捞到三年前的一篇公告："退款将在 7–15 个工作日内原路退回。" 生成器照抄，答了 7–15 个工作日。实际上今年的政策已经改成 1–3 个工作日，新文档就在库里，只是排在第 5，被截断在 top-3 之外。

问题不在生成，而在证据链的前三环：

| 环节 | 这次发生了什么 | 对应概念 |
|---|---|---|
| 查询 | "退款多久到账"没带产品线，召回混进旧公告 | 查询构造（query construction） |
| 召回 | 旧公告标题相似度高，挤进前三 | 召回（recall） |
| 排序 | 没有按发布时间加权 | 重排（rerank）与时效（freshness） |
| 生成 | 只抄了单一来源，没有交叉核对 | 证据使用（grounding） |

**召回是什么？** 人话：先把"可能相关"的都捞出来，宁多勿漏。类比：去图书馆先把 20 本可能相关的书借到手，再决定读哪几页。例子：新旧两篇公告都该被捞出来，漏掉新的那篇，后面再怎么排都错。

**重排是什么？** 人话：把最该看的几段排到最前面。类比：20 本书按相关度排序，只精读前 3 本。例子：新公告应该排到第一；如果排序模型只看语义相似度，旧公告的"7–15 个工作日"反而更贴合问句。

**时效（freshness）是什么？** 人话：这条证据今天还算不算数。类比：冰箱里的牛奶先看保质期，再看牌子。例子：文档带 `effective_date`，超期片段降权或标注"历史政策"，必要时强制检索最新版本。

下面按流水线拆开：查询改写、召回、重排、组装、生成、核对，每一段都有自己的失败模式。

## 问题与边界

- **解决什么**：RAG 流水线每一段的做法与失败模式；分块、混合检索、重排、查询改写；agentic RAG 的迭代与停止条件；分环节评测；以及"什么时候不该用 RAG"。
- **不解决什么**：不讨论记忆的写入、去重与遗忘（见[记忆体系](03-memory.md)），不讨论上下文预算与压缩（见[上下文工程](02-context-engineering.md)），不比较具体向量库。
- **与相邻概念的分界**：RAG 是**只读**的外部知识检索；记忆是读写闭环；微调是把知识放进权重。三者解决的是不同问题，不能互相替代。

## 流水线与度量

```mermaid
flowchart LR
    Q[用户问题] --> RW[查询改写]
    RW --> R[召回 BM25 + 向量]
    R --> RR[重排]
    RR --> A[组装: 去重/截断/引用]
    A --> G[生成]
    G --> V[核对引用]
    V -->|证据不足| RW
```

| 环节 | 常见做法 | 典型失败 | 度量 |
|---|---|---|---|
| 查询改写 | 同义扩展、拆子问题、HyDE | 改写偏离原意 | 改写后召回提升 |
| 召回 | BM25、向量、混合 | 漏掉精确 ID / 召回噪声大 | recall@k |
| 重排 | cross-encoder、LLM 重排 | 成本高、延迟翻倍 | nDCG@k |
| 组装 | 去重、按相关度排序、加来源 | 超预算、关键段被截断 | 有效 token 占比 |
| 生成 | 带引用作答、拒答 | 编造引用、忽略证据 | faithfulness |
| 核对 | 断言-证据对齐 | 引用与结论不符 | citation accuracy |

这张表的用法是**定位**：端到端效果差时，先看哪一段的指标掉了，而不是直接换更大的模型。

## 关键机制

### 分块

分块决定了召回的上限——块切错了，后面所有环节都在补救。四种策略：

- **固定长度**：实现最简单，容易在句子中间切断。
- **按结构**：按标题、段落、代码块切，保留语义边界，是默认首选。
- **父子块**：小块用于检索（精度高），大块用于生成（上下文全），两全但实现复杂。
- **语义分块**：用模型判断断点，成本高，收益不稳定。

两个容易被忽略的细节：**块要带上下文**（标题、所属章节、文档名），否则"该参数默认 30 秒"这种块离开标题就无法判断说的是什么；**块要带稳定 ID**，否则引用与增量更新都做不了（[Anthropic 的 contextual retrieval](https://www.anthropic.com/news/contextual-retrieval) 就是给块补上下文，厂商报告称失败检索减少约 49%）。

### 混合检索

纯向量检索在两类查询上会输：**精确标识符**（订单号、错误码、函数名）和**罕见专有名词**。BM25 在这两类上仍然更强，所以生产系统普遍做混合检索，再用融合（RRF 或加权）合并。代价是要维护两套索引与两套调参。

### 重排

召回追求"不漏"，重排追求"把对的放前面"。cross-encoder 重排通常能显著提升 top-3 的准确率，代价是每候选一次前向，延迟与成本随候选数线性增长。常见折中是召回 50–100 条、重排到 5–10 条、再进上下文。

### 查询改写

用户的问法与文档的写法往往不一致，改写是性价比最高的一环：

- **同义与术语对齐**：把口语映射到文档术语；
- **拆子问题**：多跳问题拆成可分别检索的子查询；
- **HyDE**：先生成一个假设答案再拿它去检索，适合问题短、文档长的场景；
- **多查询**：生成 2–3 个变体并行召回再合并。

改写的风险是**偏离原意**，所以要有回退：改写后的召回如果明显变差，用原查询重试。

### Agentic RAG

把检索做成工具之后，流程从"一次检索 → 一次生成"变成"检索 → 评估证据 → 再检索"。三个设计点：

1. **什么时候再检索**：证据不足、来源冲突、问题被拆出新子问题时。
2. **什么时候停**：达到证据充分性阈值、预算耗尽、或连续两轮没有新增有效信息。
3. **怎么防止打转**：查询指纹去重、限制轮次、强制在最后一轮给出"已知/未知"的边界。

> 判断：agentic RAG 的收益主要来自"多跳与冲突消解"，不是"检索次数更多"。对单跳事实问题，多轮检索通常只是增加成本。

### 引用与核对

引用不是装饰，是让答案可被验证的最小机制。三个要求：引用到**具体片段**（不是整篇文档）、引用**真的支持该结论**、以及**允许拒答**。没有拒答能力的 RAG，遇到检索不到的问题一定会编。

### GraphRAG 的适用面

当问题需要"全局聚合"（这批文档的主要主题是什么）或"多跳关系"（A 的供应商的母公司还供应谁）时，图结构比扁平块更有优势。代价是抽取成本与模式设计，且更新麻烦。判断标准：**关系本身是不是查询目标**——是，才值得上图。

## 评测

分环节与端到端要分开测，否则无法定位问题：

| 层次 | 指标 | 说明 |
|---|---|---|
| 召回 | recall@k、MRR | 正确答案是否在候选里 |
| 重排 | nDCG@k | 对的排得够不够前 |
| 生成 | faithfulness、answer correctness | 是否忠于证据、是否答对 |
| 引用 | citation accuracy | 引用是否真的支持结论 |
| 端到端 | 任务成功率、拒答准确率 | 该答的答对、不该答的拒答 |

黄金集的构造比指标更重要：**从真实问题里采样**，覆盖高频、长尾、多跳、无答案四类；无答案样本必须占一定比例，否则测不出幻觉。

### 一个最小可用的 RAG 骨架

按下面的顺序搭，每一步都能独立验证，不要一次上全套：

1. 文档按结构切块，每块带上标题与所属章节。
2. 混合召回取 top-50（BM25 + 向量，RRF 融合）。
3. 重排到 top-8，进上下文前按相关度与篇幅截断。
4. 生成时要求逐句引用，并允许回答"资料中没有"。
5. 后处理校验引用是否真的支持结论，不支持则重写或降级。
6. 把线上问题与失败样本沉淀成黄金集，按周回归。

这套骨架里，第 4、5 步决定"敢不敢上线"，第 6 步决定"能不能变好"；前三步只决定"能不能跑"。

## 什么时候不该用 RAG

| 场景 | 更合适的做法 | 原因 |
|---|---|---|
| 结构化聚合（求和、分组、排序） | SQL / 数据仓库 | 检索解决不了计算 |
| 精确计数与规则判断 | 代码 | 模型数不准 |
| 强实时数据 | 直接调 API | 索引天然滞后 |
| 权限差异极大 | 检索前做权限过滤 | 召回后再过滤会泄露 |
| 知识只在一个人脑子里 | 访谈、写文档 | RAG 不能无中生有 |

## 常见坑

- **坑 1：迷信 top-k**。触发条件：效果不好就把 k 调大。后果：噪声进上下文，模型被干扰，成本上升。规避：先看 recall@k 是否已饱和，再调重排与阈值。
- **坑 2：块切断语义**。触发条件：固定长度切分且不重叠。后果：答案被切成两半，两半都召不回。规避：按结构切 + 适度重叠 + 块带标题。
- **坑 3：没有重排**。触发条件：只用向量相似度取 top-5。后果：语义相近但不回答问题的块排在前面。规避：加 cross-encoder 或 LLM 重排。
- **坑 4：索引陈旧**。触发条件：文档更新但索引按周重建。后果：答的是旧政策，且看起来有理有据。规避：增量索引 + 文档版本号 + 过期标记。
- **坑 5：引用缺失或造假**。触发条件：让模型"顺便标个来源"。后果：引用与结论对不上，比没有引用更危险。规避：先生成断言再匹配证据，或要求逐句引用并在后处理校验。
- **坑 6：检索内容挤掉系统指令**。触发条件：把长文档整篇塞进用户消息。后果：格式与禁区被淹没。规避：检索内容后置、限额、关键约束在末尾复述（见[上下文工程](02-context-engineering.md)）。
- **坑 7：把 RAG 当记忆**。触发条件：用向量库存对话历史并宣称有记忆。后果：记不住冲突、删不掉、越用越偏。规避：区分只读知识与读写记忆（见[记忆体系](03-memory.md)）。

## 开放问题

- **证据充分性**：模型如何判断"够了"？目前靠提示词与启发式，缺可校准的方法。
- **多跳的停止条件**：链式检索到第几跳该停，没有通用答案。
- **引用粒度**：句级、段级还是 span 级？粒度越细成本越高，但可验证性越好。
- **权限与召回的统一**：预过滤损失召回，后过滤有泄露风险，两者能否在索引层统一？
- **评测污染**：公开 QA 集被训练数据覆盖后，RAG 评测还剩下多少有效性？
